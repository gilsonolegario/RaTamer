## Task 2b — Fix battery-row race (approved scope addition)

Approved by the user after Task 2 discovery. The menu-bar popover and the
Settings → General battery row almost never rendered because two threads raced
for the single-slot HID mailbox: the `RatTamer.ButtonLoop` thread (polls
`readReport(timeout: 0.05)` continuously) and the synchronous `request()` reads
(e.g. `BatteryMonitor.refresh` → `getBatteryInfo`). The loop almost always
consumed the battery reply first, so `request()` timed out and `info` stayed
`nil` (confirmed 3/3 failed popover opens; `RatDiagnose`, which has no loop
thread, always succeeded).

**Fix applied:**
- `HIDDevice.swift`: added `readForRequest(timeout:)`, `beginRequest()`,
  `endRequest()` to the protocol with default no-op implementations.
- `IOHIDDeviceWrapper.swift`: `read(timeout:)` now refuses to consume the
  mailbox while `inFlightRequests > 0` (waits on the same `NSCondition`);
  `readForRequest(timeout:)` consumes directly; `beginRequest()` /
  `endRequest()` bump the counter and broadcast.
- `HIDPPSession.swift`: `request()` brackets itself with
  `beginRequest()` / `endRequest()` (deferred even on throw) and reads via
  `readForRequest` so it never blocks on its own gate.

The loop thread therefore cannot steal a request's reply. Residual (pre-existing,
out of scope): two concurrent `request()`s can still steal each other's replies;
single-slot mailbox still drops a report that overwrites a pending one.

**Verified:** `swift build` green; `swift test` 151/151; 3/3 fresh app launches
show the popover at height 214 (battery row "Battery: Full") on first open.

## Task 3 — README rewrite

Rewrite `README.md` per spec sections C, D, E:

- Title + one-line pitch; hero image `screenshots/settings-about.png`;
  badges row (Swift 5.9, macOS 14+ via shields.io); **no license badge**.
- Features table (menu bar/battery, DPI cycle, swap Left/Right, thumb wheel,
  SmartShift sensitivity + scroll inversion, gestures, icon/About).
- Requirements / Permissions / Build and run (kept, concise).
- How it works: keep the current divert-based bullets **and** the architecture
  diagram, but point the reader to the Advanced section.
- **Advanced: the HID++ protocol** — the full deep-dive from spec section D:
  framing (short 0x10 / long 0x11, body
  `[device, feature, (functionID<<4)|softwareID, params]`), feature discovery
  (Root 0x0000 getFeature, index learned at runtime — not stable), the 8
  controls table (0x0050/51/52/53/56/0x00C3/0x00C4/0x00D7), function nibbles
  (0x00 getCount, 0x01 getControlInfo, 0x02 getCidReporting, 0x03
  setCidReporting), reporting flags (divert 0x01, divert-valid 0x02, rawXY
  0x10, rawXY-valid 0x20), diverted event `11 <dev> <feat> 00 <cid×4>` (state
  report), raw XY event `… 10 <dx> <dy>` (Int16 BE signed), response matching,
  and the hardware gotchas (IOHIDManager doesn't enumerate → registry path;
  Output-only writes with full 20-byte buffer; cold-start >0.5s retry 3×0.5s).
- **Distribution** — the 2 paths from spec section E (local build recommended;
  ad-hoc Release zip + `xattr -dr com.apple.quarantine` / Open Anyway) with the
  notarization note.
- Configuration / RatTest / Diagnostics: keep, verify commands exist.
- History: close the Python chapter cleanly.
- Keep every command/file factual (verified against the repo).
